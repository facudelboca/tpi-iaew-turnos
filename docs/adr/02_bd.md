# ADR-002: Base de datos y Control de Concurrencia Transaccional

**Estado:** Aceptado

**Contexto:**
El dominio del sistema corresponde a la **Reserva de Turnos de Salud**, que comprende las entidades `Paciente`, `Profesional`, `Especialidad`, `ProfesionalDiaAtencion`, `Turno` y `EventoProcesado`. Este tipo de sistema exige:
1. **Integridad referencial estricta:** Un turno debe asociarse a un paciente, profesional y especialidad válidos.
2. **Garantía absoluta de no solapamiento:** La agenda de un profesional de la salud jamás puede registrar dos turnos superpuestos en un mismo horario, incluso ante picos de concurrencia de múltiples solicitudes en simultáneo compitiendo por el mismo slot.
3. **Idempotencia y auditoría:** Se debe registrar la clave de idempotencia de cada reserva para evitar cargos o registros duplicados por reintentos de red, y registrar los eventos procesados para evitar duplicación de notificaciones.

**Decisión:**
Adoptar **PostgreSQL 16** como motor relacional principal gestionado mediante **Sequelize ORM** para Node.js, complementado con scripts DDL SQL versionados (`src/migrations/init.sql` y `src/migrations/002_resiliencia_idempotencia.sql`):

1. **Control de Concurrencia Pesimista (ACID):**
   Para garantizar la serialización estricta y eliminar condiciones de carrera en reservas simultáneas, la operación de reserva se ejecuta dentro de una transacción con aislamiento ACID y bloqueo de fila a nivel de base de datos (`SELECT ... FOR UPDATE` sobre el registro del `Profesional`). Esto fuerza la resolución secuencial en PostgreSQL: la primera transacción adquiere el lock y confirma el turno (`201 Created`), mientras que las transacciones competidoras leen el turno recién insertado y son rechazadas determinísticamente con error tipificado `409 Conflict (TURNO_OCUPADO)`.
2. **Esquema de Idempotencia y Resiliencia:**
   - La tabla `turnos` incluye la columna `idempotency_key VARCHAR(128)` con restricción `UNIQUE`, protegiendo la consistencia tanto a nivel de middleware como a nivel de motor de base de datos.
   - Se crea la tabla dedicada `eventos_procesados` (`event_id VARCHAR(128) PRIMARY KEY`, `type`, `turno_id`, `fecha_procesamiento`) para soportar consumo idempotente de mensajes en el worker de RabbitMQ con semántica *at-least-once*.
3. **Restricciones de Integridad:**
   - `ON DELETE RESTRICT` en claves foráneas de turnos y especialidades para prevenir borrados accidentales de historiales clínicos.
   - `ON DELETE CASCADE` en las disponibilidades horarias (`profesionales_dias_atencion`).
   - Índices compuestos optimizados sobre `(profesional_id, fecha_hora_inicio, estado)` y `(paciente_id, fecha_hora_inicio)` para agilizar consultas de disponibilidad y validaciones de solapamiento.

**Alternativas consideradas:**
- **MongoDB / NoSQL (Documental):** Descartado. No ofrece bloqueos pesimistas de fila ni restricciones de integridad referencial nativas entre colecciones distintas sin implementar transacciones multi-documento complejas en la capa de aplicación, elevando el riesgo de dobles reservas (*phantom reads*).
- **Bloqueo Optimista (version column):** Descartado para la reserva de turnos en caliente. Ante alta contención sobre el mismo horario, el bloqueo optimista genera múltiples abortos y reintentos fallidos en cascada; el bloqueo pesimista en PostgreSQL resuelve la contención de forma inmediata en una única pasada con rechazo determinístico 409.

**Consecuencias:**
- Cero colisiones de turnos bajo pruebas de estrés concurrentes (verificado con 30 peticiones paralelas: 1 reserva exitosa y 29 conflictos 409 controlados).
- Persistencia confiable con integridad referencial ACID.
- Contenedor PostgreSQL orquestado en `docker-compose.yml` (`iaew-turnos-postgres`) con healthcheck mediante `pg_isready`.
